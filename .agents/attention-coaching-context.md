## 1. 검출기 출력 7종

카메라에서 영상을 받아 MediaPipe로 얼굴 특징을 뽑고 모델에 넣는 흐름 전체를 하나의 **검출기**로 본다.
검출기가 내놓는 값은 아래 일곱 가지 중 하나다. **브라우저 안에서만 쓰는 층위**다.

| 출력 | 언제 | 값이 정해지는 시점 |
|---|---|---|
| `Not-Engaged` (1단계) | 카메라 정상 + 얼굴 특징 확보 | 10초를 관측한 뒤 |
| `Barely-Engaged` (2단계) | 〃 | 10초를 관측한 뒤 |
| `Engaged` (3단계) | 〃 | 10초를 관측한 뒤 |
| `Highly-Engaged` (4단계) | 〃 | 10초를 관측한 뒤 |
| `UNMEASURABLE` | 카메라는 영상을 보내는데 얼굴 특징을 못 뽑음 | 10초를 관측한 뒤 |
| `CAMERA_OFF` | 카메라가 쓸 만한 영상을 내보내지 않음 | 그 자리에서 바로 |
| `DETECTOR_UNAVAILABLE` | 검출기 자체가 돌지 못함 (MediaPipe·ONNX 로드 실패 등) | 그 자리에서 바로 |

### 1.1 어느 출력을 낼지 정하는 순서

조건이 동시에 성립하는 경우가 있다. 카메라가 꺼지면 얼굴도 당연히 안 잡히고,
모델을 못 불러왔는데 카메라까지 꺼져 있을 수도 있다.
위에서부터 검사해 **처음 걸린 것을 내놓고 멈춘다.**

```
1. 검출기를 못 불러왔는가         →  DETECTOR_UNAVAILABLE
2. 카메라가 쓸 만한 영상을 주는가  →  CAMERA_OFF
3. 10초 창에 얼굴이 충분한가      →  UNMEASURABLE
4. 그 외                         →  모델이 낸 4단계
```

근본적인 실패를 먼저 보는 이유는 **학생에게 할 수 없는 일을 시키지 않기 위해서**다.
모델을 못 불러왔는데 카메라도 꺼진 학생에게 `CAMERA_OFF` 로 알리면 "카메라를 켜주세요"가 뜬다.
켜도 분석은 안 된다. 헛수고를 시키는 셈이다.

### 1.2 UNMEASURABLE 일 때는 모델을 돌리지 않는다

얼굴 특징을 못 뽑았으면 모델에 넣을 입력이 없다. 그래도 억지로 돌리면 모델은 4단계 중 아무 값이나 내놓고,
그 값이 그럴듯해 보이기 때문에 오히려 더 위험하다. **모델을 건너뛰고 곧바로 `UNMEASURABLE` 을 낸다.**

이전 판에 있던 **룰 폴백은 두지 않는다.** 모델이나 MediaPipe 를 못 불러오면
`DETECTOR_UNAVAILABLE` 로 판정만 비활성하고 수업은 그대로 진행한다.

### 1.3 CAMERA_OFF 가 덮는 범위

학생이 직접 끈 경우만이 아니라 **카메라가 쓸 만한 영상을 내보내지 못하는 모든 상황**을 여기 넣는다.

- 학생이 카메라를 끔
- 브라우저에서 카메라 권한을 거부함
- 다른 앱이 카메라를 점유하고 있음
- 카메라 하드웨어가 동작하지 않음

판별은 카메라 트랙 상태로 한다. 트랙이 없거나, `readyState` 가 `"ended"` 거나, `muted` 가 `true` 면 이 상태다.

범위를 이렇게 넓히면 `UNMEASURABLE` 에는 **"영상은 들어오는데 얼굴이 안 보인다"** 는 경우만 남는다.
장비 문제가 섞이지 않으므로 §7.2 에서 이 상태를 트리거 분자에 넣는 근거(화면을 벗어났다는 증거)도 정확해진다.

### 1.4 검출기는 확률까지 함께 내놓는다

모델은 4단계 중 하나를 집어주는 게 아니라 네 단계 각각의 확률을 준다.
검출기는 **어느 단계인지와 확률 네 개를 같이** 내놓는다. 확률을 쓰는 이유는 §3.3 에 있다.

## 2. 학생 상태 6종

§1 의 검출기 출력을 프롬프트 응답과 합쳐 정해지는 값이다. **서버로 보내고 집계에 쓰는 층위**다.

| 상태 | 언제 | 프롬프트 | 트리거 분자 | 분모 |
|---|---|---|---|---|
| `GOOD` | 검출기가 **3·4단계**, 또는 이해 확인에 "이해했어요" 응답 | — | ✕ | 포함 |
| `CONFUSED` | 저참여 3연속 → 이해 확인에 "헷갈려요" | 이해 확인 | **○** | 포함 |
| `MISSED` | 저참여 3연속 → 이해 확인에 "놓쳤어요" | 이해 확인 | **○** | 포함 |
| `NON_RESPONSE` | 저참여 3연속 → **30초 무응답** | 이해 확인 | **○** | 포함 |
| `UNMEASURABLE` | 검출기 `UNMEASURABLE` **3연속** | 자세 안내 | **○** | 포함 |
| `CAMERA_OFF` | 검출기 `CAMERA_OFF` | 카메라 안내 | ✕ | **1분 지속 시 제외** |

- **검출기 3·4단계면 프롬프트 없이 바로 `GOOD`.** 프롬프트는 저참여 3연속일 때만 뜬다.
- 표기는 **언더스코어**(`NON_RESPONSE`, `CAMERA_OFF`)로 통일한다 — enum·JSON·DB 공통.
- 두 층위를 같은 이름으로 부르지 않는다. `UNMEASURABLE` 은 양쪽에 있지만
  검출기 쪽은 10초 판정 한 건, 학생 상태 쪽은 3연속으로 확정된 값이다.

### 2.1 DETECTOR_UNAVAILABLE 은 서버로 보내야 한다

검출기가 못 도는 학생은 관측이 불가능하므로 **분모에서 빠져야** 한다.
그러려면 서버가 그 사실을 알아야 하고, 아무것도 보내지 않으면 네트워크가 끊긴 것과 구분되지 않는다.
그래서 `DETECTOR_UNAVAILABLE` 은 다른 상태와 똑같이 10초마다 전송한다.

⚠️ **머지된 백엔드(`AttentionState`, 티켓 78)는 6종만 받는다.** 이 문서 기준으로 **계약을 넓혀야 한다.**
`CAMERA_OFF` 로 합치면 학생에게 "카메라를 켜주세요"가 뜨는데 켜도 해결되지 않으므로 대안이 되지 못한다.
필요한 변경은 §11 의 "티켓 본문과 어긋나는 항목" 표에 적었다.

## 3. 10초 판정

### 3.1 창 구성

| 항목 | 값 |
|---|---|
| 판정 주기 | 10초에 한 번 |
| 프레임 표본 추출 | 초당 10장, 창 하나에 100장 |
| 창 내부 구간 | 20개 × 각 500ms |

구간을 나누는 이유는 모델이 10초를 시간 순서가 있는 20개 토막으로 받기 때문이다.
각 구간에서 특징값의 **평균과 표준편차**를 뽑아 모델에 넣는다.

실제 배포 계약은 `mediapipe_98_v1` 이다. 프레임 하나에서 49차원을 뽑고,
구간마다 평균 49 + 표준편차 49 = 98 을 만들어 `20 × 98` 텐서로 넣는다.

### 3.2 UNMEASURABLE 로 판정하는 기준

**유효 프레임**은 프레임이 도착했고 그 프레임에서 얼굴까지 잡힌 것을 뜻한다.
프레임이 아예 도착하지 않은 경우도 유효하지 않은 것으로 센다. 즉 아래 둘을 구분하지 않는다.

- 프레임이 안 왔다 (기기 성능 부족, 탭 숨김, CPU 부하)
- 프레임은 왔는데 얼굴이 없다 (자리를 비움, 역광, 카메라 각도)

**분모는 기대 프레임 수 100장으로 고정한다.** 실제로 도착한 장수가 아니다.

아래 둘 중 하나만 걸려도 모델을 건너뛰고 `UNMEASURABLE` 을 낸다.

1. 창 전체 유효 프레임이 **70% 미만** (100장 중 70장 기준)
2. **20구간 중 어느 한 구간이라도 유효 프레임이 3장 미만** (구간당 기대 5장)

조건이 둘인 이유는 서로 다른 것을 잡기 때문이다. 전체 비율만 보면 아래 두 경우가 똑같이 70%로 통과한다.

```
A:  ●●●●●●●○○●●●●●●●○○●●   유효 프레임이 고르게 퍼져 있다
B:  ●●●●●●●●●●●●●●○○○○○○   앞 7초에만 몰려 있고 뒤 3초가 통째로 비었다
```

모델은 10초를 시간 순서로 읽는다. B 를 넣으면 **뒤 3초 구간의 입력은 사실상 지어낸 값**이 된다.
학생이 창 중간에 자리를 뜨면 정확히 이 모양이 나온다.
**전체 조건은 전반적으로 부족한 창을, 구간 조건은 한쪽에 몰린 창을 걸러낸다.**

구간 최소를 3장으로 잡은 이유는 모델 입력이 구간별 평균과 **표준편차**이기 때문이다.
유효 프레임이 1장이면 표준편차가 항상 0이 되고, 모델은 그 0 을
"이 0.5초 동안 완벽하게 정지해 있었다"로 읽는다. 관측이 부족했을 뿐인데
"매우 안정적으로 집중하고 있다"는 신호가 전달된다. 없는 정보를 지어내서 넘기는 셈이다.
2장이면 표준편차가 두 값 차이의 절반이라 우연히 비슷하게 찍힌 것과 구분되지 않는다.

전체 조건과의 관계도 3장이 맞다. 구간 최소를 정하면 창 전체 최소 장수가 따라 정해진다.

| 구간 최소 | 창 전체 최소 | 전체 70% 조건(70장)과의 관계 |
|---|---|---|
| 2장 | 40장 | 70% 쪽이 훨씬 엄격해 구간 조건이 잘 안 걸린다 |
| **3장** | **60장** | 60장과 70장이라 가깝다. 두 조건이 각자 제 역할을 한다 |
| 4장 | 80장 | 구간 쪽이 더 엄격해 70% 가 죽은 값이 된다 |

⚠️ **70% 에는 근거 데이터가 없다.** 정상적으로 수업을 듣는 학생의 얼굴 검출률을 재본 적이 없다.
설정 상수로 빼두고 실사용 전에 한 번 측정해서 조정한다.

### 3.3 저참여로 보는 기준 — 확률 합 0.35

모델은 네 단계 각각의 확률을 준다. 그런데 필요한 값은 하나뿐이다.
**아래쪽 두 단계일 확률이 얼마인가.**

```
모델 출력:  1단계 0.20  2단계 0.15  3단계 0.60  4단계 0.05
저참여 확률 = 0.20 + 0.15 = 0.35
```

**저참여 확률이 0.35 이상이면 저참여로 센다.**

| 모델 출력 (1·2·3·4단계) | 저참여 확률 | 기준 0.5 | 기준 0.35 |
|---|---|---|---|
| `0.05 / 0.10 / 0.25 / 0.60` | 0.15 | 고참여 | 고참여 |
| `0.20 / 0.15 / 0.60 / 0.05` | 0.35 | 고참여 | **저참여** ← 갈린다 |
| `0.30 / 0.25 / 0.35 / 0.10` | 0.55 | 저참여 | 저참여 |

가운데 줄이 핵심이다. 확률이 가장 높은 건 3단계(0.60)지만
모델은 **"3단계 같긴 한데 확신은 없다"** 고 말하는 중이다.
가장 높은 단계만 고르는 방식은 기준 0.5 와 사실상 같아서 이걸 고참여로 넘겨버린다.

기준을 낮춘다는 건 "의심스러우면 저참여로 친다"는 뜻이다. 실제로 헤매는 학생을 더 많이 잡는 대신
멀쩡한 학생도 더 자주 잘못 잡는다. **3연속 요구가 이미 오탐을 걸러주므로** 꽤 낮춰도 괜찮다.

실측 근거 (EngageNet 테스트셋 2,014건 = 저참여 516 / 고참여 1,498, e0 학습 결과):

| 기준값 | 판정 한 건 검출률 | 한 건 오탐률 | 3연속 검출률 | 90분당 잘못 뜨는 횟수 |
|---|---|---|---|---|
| 최고값만 (argmax) | 0.672 | 0.068 | 30.4% | 0.17 |
| 0.50 | 0.671 | 0.065 | 30.1% | 0.15 |
| 0.45 | 0.698 | 0.077 | 34.0% | 0.24 |
| **0.35** | 0.744 | 0.097 | **41.2%** | **0.49** |
| 0.265 | 0.775 | 0.113 | 49.4% | 1.00 |

- 확률을 안 쓰면 기준이 0.5 에 영구히 고정되고, 그 값이 최선일 이유가 없다.
- 0.35 로 낮추면 같은 모델·같은 3연속 규칙으로 검출률이 30% 에서 41% 로 오른다.
- **5개 seed 앙상블은 하지 않는다.** 49.4% → 49.8% (0.4%p) 인데 추론 비용이 5배다.

⚠️ 위 표는 인접한 10초 창이 서로 무관하다고 가정하고 계산했다. 실제로는 연속된 창끼리 값이 비슷해서
**검출률도 오탐도 표보다 높게 나올 것**이다. 순서와 자릿수는 유지되나 절대값은 실사용 로그로 보정해야 한다.

### 3.4 왜 3번 연속을 요구하는가

| 요구 연속 횟수 | 실제 저참여 검출률 | 시간당 잘못 뜸 | 90분당 잘못 뜸 |
|---|---|---|---|
| 1번 | 67.2% | 24.5회 | 37회 |
| 2번 | 45.2% | 1.7회 | 2.6회 |
| **3번** | **30.4%** | **0.12회** | **0.2회** |
| 4번 | 20.5% | 0.01회 | 0.01회 |

한 번만 저참여로 나와도 바로 띄우면 **학생 한 명이 시간당 24번 프롬프트를 받는다.**
쿨타임 5분으로 시간당 12번까지 묶어도 대부분이 잘못 뜬 것이다. 수업이 불가능해진다.

## 4. 판정 흐름

```
브라우저(학생) ── 10초 관측 ──▶ 검출기 출력 1건 (§1)
                                  │
        ┌──────────────┬──────────┴────────┬─────────────────┐
        ▼              ▼                   ▼                 ▼
     3·4단계     저참여 3연속        UNMEASURABLE 3연속   CAMERA_OFF
        │              │                   │                 │
        ▼              ▼                   ▼                 ▼
      GOOD    [이해 확인 프롬프트]      [자세 안내]      [카메라 안내]
   (프롬프트 X)        │              (쿨타임 5분)      (1분 지속 후)
                       ▼
      이해했어요 → GOOD  /  헷갈려요 → CONFUSED
      놓쳤어요 → MISSED  /  30초 무응답 → NON_RESPONSE
                       │
                       ▼
             5분 슬라이딩 윈도우에 기록 (§7)
```

- **3연속 = 30초.** 카운터를 되돌리는 규칙은 §4.1 에 있다.
- 판정은 **브라우저에서** 하고 결과만 서버로 보낸다(원본 영상 비전송, 스토리 16 원칙).

### 4.1 연속 카운터를 언제 되돌리는가

카운터가 두 개 동시에 돈다. **판정 건수를 세는 값은 이 둘뿐이다.**

| 카운터 | 3에 닿으면 |
|---|---|
| 저참여 카운터 | 이해 확인 프롬프트를 띄운다 |
| `UNMEASURABLE` 카운터 | 자세 안내 프롬프트를 띄운다 |

10초 판정이 하나 들어올 때마다 두 카운터가 각각 이렇게 움직인다.

| 들어온 판정 | 저참여 카운터 | `UNMEASURABLE` 카운터 |
|---|---|---|
| 저참여 (확률 합 0.35 이상) | 1 올린다 | 0으로 되돌린다 |
| 저참여가 아닌 4단계 | 0으로 되돌린다 | 0으로 되돌린다 |
| `UNMEASURABLE` | **그대로 유지한다** | 1 올린다 |
| `CAMERA_OFF` | 0으로 되돌린다 | 0으로 되돌린다 |
| `DETECTOR_UNAVAILABLE` | 0으로 되돌린다 | 0으로 되돌린다 |

`UNMEASURABLE` 이 끼었을 때만 저참여 카운터를 유지한다.

```
1단계 → 1단계 → UNMEASURABLE → 1단계
  1       2      (2 그대로)       3    → 프롬프트를 띄운다

1단계 → 1단계 →   3단계    → 1단계
  1       2         0           1    → 띄우지 않는다
```

한쪽만 유지하고 다른 쪽은 되돌리는 게 일관성 없어 보이지만 이유가 있다.

`UNMEASURABLE` 은 **학생 상태가 바뀐 게 아니라 관측이 비었다**는 뜻이다.
얼굴이 잠깐 안 잡혔을 뿐이고 학생이 갑자기 집중하기 시작했다는 증거는 아니다.
여기서 저참여 카운터를 되돌리면 이상한 일이 생긴다.
**집중하지 않는 학생일수록 자세가 흐트러져 얼굴 검출도 같이 실패하는데**,
그럴 때마다 카운터가 0이 되면 정작 도움이 필요한 학생이 프롬프트를 덜 받는다.

반대 방향은 되돌리는 게 맞다. `UNMEASURABLE` 카운터가 도는 중에 4단계 값이 나왔다면
그건 **관측이 실제로 됐다는 확실한 증거**다.

### 4.2 카메라를 켜고 끄는 시점이 창 경계와 어긋날 때

10초 창은 일정한 주기로 도는데 학생은 아무 때나 카메라를 켜고 끈다.
그대로 두면 앞 4초만 유효한 창처럼 애매한 조각이 생긴다.

§1 에서 출력을 두 부류로 나눈 것이 여기서 쓰인다.

| 부류 | 출력 | 판정 방식 |
|---|---|---|
| 10초를 봐야 아는 것 | 4단계, `UNMEASURABLE` | 창이 끝나야 값이 나온다 |
| 보는 순간 아는 것 | `CAMERA_OFF`, `DETECTOR_UNAVAILABLE` | 그 순간 확정된다 |

아래 둘은 관측 결과가 아니라 **이미 알고 있는 사실**이다. 10초를 기다릴 이유도, 모델을 돌릴 이유도 없다.

> `CAMERA_OFF` 나 `DETECTOR_UNAVAILABLE` 로 바뀌면 진행 중이던 창을 버리고 그 자리에서 보고한다.
> 그 상태에서 벗어나면 벗어난 시점부터 새 10초 창을 시작한다.

애매한 조각 창이 생기지 않는다. 대신 카메라를 켠 뒤 첫 판정까지 10초를 기다려야 한다.
강의실에 처음 들어올 때도 마찬가지다.

받아들인 부작용이 하나 있다. 카메라를 껐다 켰다 반복하면 창이 계속 처음부터 다시 시작해서
4단계 판정이 한 번도 나오지 않는다. 판정을 피할 수 있다는 뜻이다.
다만 그 동안 `CAMERA_OFF` 가 계속 서버로 가므로 기록은 남는다.

### 4.3 탭이 숨겨졌을 때

**탭이 숨겨져도 측정을 계속하는 구조로 만든다.**
`requestAnimationFrame` 으로 루프를 돌리는 대신 Worker 에서 카메라 트랙을 직접 읽어,
타이머가 아니라 프레임이 도착하는 것 자체가 루프를 굴리게 한다.

| 방식 | 탭이 숨겨지면 |
|---|---|
| `requestAnimationFrame` | 콜백이 아예 돌지 않는다 (HTML 명세) |
| `setInterval` | 최소 1초 간격으로 늦춰진다. 초당 10장이 1장으로 떨어진다 |
| 카메라 트랙 | 그대로 흐른다. 카메라가 꺼지는 게 아니다 |
| Worker 에서 트랙 직접 읽기 | 확인하지 못했다. **실제로 재봐야 한다** |

- **선행 작업**: 숨겨진 탭에서 초당 10장이 유지되는지 측정한다.
  안 나오면 유효 프레임 비율이 70% 에 못 미쳐 자동으로 `UNMEASURABLE` 로 떨어진다.
- **탭이 숨겨진 동안에는 프롬프트를 띄우지 않는다.** 안 보이는 화면에 띄워도
  30초 뒤 무응답으로 닫히고 쿨타임만 헛되게 소진된다.
- **연속 카운터는 탭이 숨겨져 있어도 그대로 계속 센다.**
- **탭이 숨겨졌다는 사실은 서버에 보내지 않는다.** 프롬프트 억제에만 쓴다.

받아들인 위험이 둘 있다. §9.2 에 근거와 함께 남겼다.

## 5. 학생 프롬프트 3종

| 종류 | 발동 | 문구 | 선택지 | 노출 | 쿨타임 |
|---|---|---|---|---|---|
| 이해 확인 | 저참여 3연속 | (기존 문구 유지) | 이해했어요 / 헷갈려요 / 놓쳤어요 | 30초 | **5분** |
| 자세 안내 | `UNMEASURABLE` 3연속 | "카메라에 얼굴이 나오도록 조정해주세요" | 확인 | 30초 | **5분** |
| 카메라 안내 | `CAMERA_OFF` **1분 지속** | §5.2 의 원인별 문구 | 지금 켤게요 / 못 켜요 | 30초 | 5분 뒤 재권유 |

### 세 프롬프트에 공통으로 적용되는 규칙

| 항목 | 값 |
|---|---|
| 화면에 띄워두는 시간 | 30초 |
| 떠 있는 동안 같은 조건이 또 성립하면 | 무시한다 |
| 떠 있는 동안 | **저참여 카운터와 `UNMEASURABLE` 카운터를 멈춘다** |
| 닫힐 때 | 그 두 카운터를 0으로 되돌린다 |
| 쿨타임을 재는 기준 시각 | 프롬프트가 닫힌 시각 |
| 쿨타임의 범위 | **프롬프트 종류별로 따로 잰다** |
| 떠 있는 동안 서버 전송 | 그대로 계속한다. 카운터만 멈춘다 |

**"떠 있는 동안 카운터를 멈춘다"는 규칙 하나가 프롬프트끼리 겹치는 문제를 없앤다.**
프롬프트가 떠 있는 30초 동안은 어떤 발동 조건도 성립할 수 없으므로,
어느 프롬프트가 더 급한지 따지는 우선순위 규칙을 만들 필요가 없다.

근거는 **프롬프트가 떠 있는 동안의 관측을 믿을 수 없다**는 데 있다.
학생은 화면 아래쪽 패널을 읽는 중이다. 시선이 내려가고, 무엇을 고를지 고민하느라 표정도 바뀐다.
모델은 이걸 "화면을 안 보고 있다"로 읽을 가능성이 높다.
**프롬프트가 스스로 저참여 판정을 만들어내는 셈**이다. 세 프롬프트 모두 사정이 같다.

쿨타임을 종류별로 따로 재기 때문에, 자리에서 뭘 하다 돌아온 학생은
**1분 반 사이에 하단 패널을 두 개 받을 수 있다.** 얼굴이 안 잡혀 자세 안내가 뜨고,
돌아와서 얼굴은 잡히지만 수업을 못 따라가 이해 확인이 뜨는 흐름이다.
따로 재기로 한 이유는 자세 안내와 이해 확인의 무게가 다르기 때문이다.
자세 안내는 확인 버튼 하나뿐이고 상태를 남기지 않는다. 이해 확인은 트리거 분자에 직접 들어간다.
쿨타임을 공유하면 자세 문제가 잦은 학생이 이해 확인을 거의 받지 못해 분자에서 빠지게 된다.

### 5.1 자세 안내

`UNMEASURABLE` 3연속(30초)에 뜬다. 이전 판의 "쿨타임 무시"를 **5분**으로 바꿨다.
반복 상한이 없으면 자리를 비운 학생에게 30초마다 계속 뜬다.

프롬프트가 떠 있는 동안 얼굴이 다시 잡혀도 **30초를 그대로 유지한다.**
얼굴 검출은 프레임 단위로 흔들려서 "해결됐다"고 판단하기가 불안정하다.

### 5.2 카메라 안내

`CAMERA_OFF` 가 **1분 이어지면** 뜬다. 분모에서 빼는 시점(§7.1)과 같은 값이다.

| 선택 | 결과 |
|---|---|
| 지금 켤게요 | 5분 뒤에도 여전히 꺼져 있으면 다시 권한다 |
| 무응답 (30초) | "지금 켤게요"와 같게 5분 뒤 재권유 |
| 못 켜요 | 수업이 끝날 때까지 다시 띄우지 않는다 |

도중에 카메라를 켜면 그 자리에서 닫는다. 목적이 달성됐으니 띄워둘 이유가 없다.

**응답은 집계를 바꾸지 않는다.** 이전 판에서는 "예"를 누르면 트리거 분모에서 빠지기로 되어 있었다.
그러면 학생 입장에서 "예"를 누르는 게 언제나 유리해진다. 프롬프트도 사라지고 집계에서도 빠지기 때문이다.
반면 "아니오"는 얻는 게 하나도 없다. 결국 모두가 "예"를 누르고 분모가 계속 줄어든다.
분모가 작아지면 소수 인원이 강사 알림 전체를 좌우한다.
집계에서 빼는 판단을 카메라가 꺼져 있는 시간으로 자동화하면 이 문제가 사라진다.
학생이 무엇을 답해도 집계는 달라지지 않으니 답을 왜곡할 이유가 없다.

**띄우는 문구는 원인에 따라 바꾼다.** 상태는 `CAMERA_OFF` 하나지만 안내는 달라야 한다.

| 원인 | 문구 |
|---|---|
| 학생이 직접 끔 | "카메라를 켜주세요" + 선택지 두 개 |
| 브라우저 권한 거부 | "브라우저에서 카메라 권한을 허용해주세요" — 답이 정해진 상황이라 선택지를 묻지 않는다 |
| 트랙이 `muted` | "다른 앱이 카메라를 사용 중인지 확인해주세요" |

### 5.3 이해 확인

저참여 3연속(30초)에 뜬다. 30초가 지나면 자동으로 닫고 `NON_RESPONSE` 로 남긴다.
세 프롬프트 중 **무응답이 상태로 남는 것은 이해 확인뿐**이다.

## 6. 서버로 보내는 것

| 항목 | 결정 |
|---|---|
| 보내는 주기 | 상태가 바뀌지 않아도 **10초마다 계속** 보낸다 |
| 보내는 값 | **검출기 출력 7종을 그대로** (§1). 4단계를 접지 않는다 |
| 이해 확인 응답 | 따로 보낸다 (`OK` / `CONFUSED` / `MISSED` / `NO_RESPONSE`) |
| 카메라 안내 응답 | 보내지 않는다. 집계에 쓰이지 않기 때문이다 |
| 자세 안내 응답 | 보내지 않는다. 확인 버튼 하나라 정보가 없다 |

4단계를 접지 않고 그대로 보내는 이유는, 접는 순간 **모델이 실제로 어떻게 판정했는지가 사라져서**
프롬프트 응답과 짝지을 수 없기 때문이다. 응답은 사실상 정답 레이블이라 모델 개선에 쓸 수 있는데,
그 시점 모델 출력이 없으면 쌍이 만들어지지 않는다.

집계에는 4단계를 쓰지 않는다(§7.4). 전송은 하되 분자·분모 계산에서는 참여 상태만 본다.

⚠️ **머지된 백엔드(티켓 78)는 참여 상태 6종만 받는다.** 4단계 값과 `DETECTOR_UNAVAILABLE` 을
받도록 **계약을 넓혀야 한다.** 필요한 변경은 §11 의 "티켓 본문과 어긋나는 항목" 표에 적었다.

4단계를 계속 보내면 학생 개인의 참여도 시계열이 서버에 쌓인다. 브라우저에서 판정하기로 한 이유가
원본을 안 보내려는 것이었으므로 그 취지와 일부 어긋난다. 모델 개선 데이터로서의 가치와 견주어 보고
보내기로 했으며, 집계에 쓰지 않는다는 제약(§7.4)으로 용도를 묶는다.

### 6.1 상태가 안 바뀌어도 계속 보내는 이유

| | 계속 보내기 | 바뀔 때만 보내기 |
|---|---|---|
| 서버가 해야 할 일 | 마지막 값과 만료 시간만 들고 있으면 된다 | 마지막 상태를 기한 없이 보관해야 한다 |
| 학생이 사라진 걸 아는 방법 | 만료되면 자동으로 드러난다 | 따로 살아 있음을 알리는 신호가 필요하다 |
| 브라우저가 죽거나 네트워크가 끊기면 | 만료되면서 드러난다 | **아무 일 없는 듯 마지막 상태가 영원히 남는다** |

고른 이유는 트래픽이 아니라 **실패가 드러나는지**다.
§2.1 에서 `DETECTOR_UNAVAILABLE` 까지 만들어 조용한 실패를 막으려 했는데,
바뀔 때만 보내면 그 노력이 무의미해진다.

트래픽은 문제가 되지 않는다. 학생 30명이면 시간당 10,800건, 초당 3건, 시간당 2MB다.

### 6.2 서버 쪽 만료 시간

머지된 구현(`CollectAttentionEventService`, 티켓 78)은 현재 상태 키를 **30초** TTL 로 보관한다.
presence heartbeat TTL 과 같은 값이어서 분자와 분모가 같은 생존 구간을 갖는다.

판정 주기가 10초이므로 TTL 이 10초 이하면 매 주기마다 값이 비는 구간이 생긴다.
그때 집계가 조회하면 학생이 사라진 것처럼 보인다.
**티켓 78 본문의 "TTL 6초"는 판정 단위가 6초이던 시절의 값이다. 구현이 30초로 바로잡았다.**

## 7. 강사 집단 트리거

**분모** — 연속 접속 **1분**을 넘긴 학생. `CAMERA_OFF` 가 1분 이상 이어지면 뺀다
**분자** — 최근 5분 안에 `CONFUSED`·`MISSED`·`NON_RESPONSE`·`UNMEASURABLE` 이 **한 번이라도** 있었던 학생
**발동** — 분자 / 분모 ≥ **30%** 인 순간
**쿨타임** — 알림 1회 후 **10분** (팁 유형과 무관, 트리거 시각 기준)

### 7.1 분모에서 빼는 기준

`CAMERA_OFF` 나 `DETECTOR_UNAVAILABLE` 이 **연속 1분** 이상 이어지면 뺀다.
그 상태에서 벗어나면 **바로 다시 넣는다.**

빼는 데 1분이 걸리고 넣는 데는 즉시인 비대칭이지만 각각 맞다.
카메라를 켜는 순간 관측이 가능해지므로 기다릴 이유가 없고,
껐다 켰다 반복해도 빼는 데 1분이 걸려서 분모가 출렁이지 않는다.

판단은 **서버가** 한다. `CAMERA_OFF` 이벤트가 연속으로 들어오는 것을 세면 된다.
클라이언트가 "저를 빼주세요"라고 말하는 구조보다 안전하다.

### 7.2 UNMEASURABLE 은 분자에 넣고 CAMERA_OFF 는 분모에서 빼는 이유

두 상태가 비슷해 보이지만 담고 있는 정보가 다르다.

| | `CAMERA_OFF` | `UNMEASURABLE` |
|---|---|---|
| 카메라 | 꺼져 있다 | **켜져 있다** |
| 왜 그런지 알 수 있는가 | 모른다. 프라이버시·대역폭·고장·이탈 중 무엇인지 구분되지 않는다 | **자리를 비웠거나 화면을 벗어난 것이 가장 유력하다** |

카메라를 끈 학생을 문제 있는 학생으로 세면 사실상 카메라를 강제하는 셈이 된다.
반면 카메라를 켠 학생은 이미 관측에 동의한 상태이고, 그 관측 결과가 "얼굴이 없다"인 것이다.

그리고 `UNMEASURABLE` 을 분자에서 빼면 학생 입장에서 선택지가 이렇게 된다.

```
"헷갈려요"라고 답한다   →  분자에 들어간다
화면 밖으로 나가버린다  →  분자에서 사라진다
```

**듣기 싫으면 화면을 벗어나는 게 유리해진다.** §5.2 에서 카메라 안내를 고친 것과 같은 모양의 문제다.

⚠️ **"분모에는 넣고 분자에서는 뺀다"는 가장 나쁜 조합이다.**
분자에 절대 들어갈 수 없는 학생이 분모만 채우면서 비율을 묽게 만들고,
학생들이 많이 이탈할수록 알림이 안 뜨게 되어 의도와 정반대로 동작한다.

### 7.3 분자에 들어가는 기준과 남는 기간

응답 쪽과 관측 쪽을 같은 모양으로 맞췄다.

| | 이해 확인 (응답) | 자세 안내 (관측) |
|---|---|---|
| 분자에 들어가는 시점 | 저참여 3연속 → 응답 | `UNMEASURABLE` **3연속** |
| 남는 기간 | **5분** | **5분** |
| 쿨타임 | 5분 | 5분 |

`UNMEASURABLE` 을 판정 한 건으로 넣지 않는 이유는, 10초 창 하나가 `UNMEASURABLE` 인 일이 자주 생기기 때문이다.
고개를 크게 돌리거나 자세를 고쳐 앉는 것만으로도 그 10초의 검출률이 70% 에 못 미칠 수 있다.
그걸 바로 분자에 넣으면 **잠깐 몸을 움직인 학생이 이탈자로 계산된다.**

반대로 남는 기간을 그 10초로만 잡으면 다음 10초에 얼굴이 잡히는 순간 분자에서 빠진다.
그러면 화면 밖에 있다가 10초에 한 번 얼굴만 비추면 계속 빠져나갈 수 있어 §7.2 의 목적이 무너진다.

남는 기간과 쿨타임이 같은 5분이라 이어진다.

```
0분   CONFUSED 로 답함  →  0~5분 동안 분자에 들어간다
5분   쿨타임이 풀려 다시 물어볼 수 있다  →  또 CONFUSED 면 5~10분 동안 들어간다
```

결과적으로 **"프롬프트를 띄울 만한 상태가 됐다"가 곧 "분자에 들어간다"** 로 기준이 하나로 묶인다.

다만 직전 응답이 `OK` 였으면 그 5분 동안은 분자에 없다. 실제로는 헤매고 있었어도 잡히지 않는다.
`OK` 라는 답을 믿는 대가이고, §9.2 에 남긴 항목과 같은 지점이다.

### 7.4 검출기 4단계는 집계에 쓰지 않는다

**같은 일을 두 번 세게 된다.** 프롬프트가 뜬 이유가 애초에 저참여였다.
그걸 확인하려고 물어봤고 학생이 "이해했다"고 답했다.
그런데 원인이었던 4단계 값을 다시 분자에 넣으면 하나의 일을 원인과 결과 양쪽에서 세는 셈이 된다.

**학생이 직접 답한 내용이 더 믿을 만하다.** 모델은 얼굴 움직임으로 속을 추측하고, 학생은 자기 상태를 안다.
학생이 괜찮다고 답했는데 모델 값으로 뒤집으면 학생 본인보다 시스템이 학생을 더 잘 안다고 주장하는 셈이 된다.

이렇게 정하면 관측과 응답이 서로 어긋나는 상황이 애초에 생기지 않는다.

### 7.5 슬라이딩 윈도우

```
10초 버킷 × 30개 = 5분
새 10초가 들어오면 가장 오래된 10초를 버린다 (4분 50초는 그대로 유지)
```

기록 시점은 **학생이 프롬프트에 답한 시각** 기준이다.

### 7.6 팁 유형 선택

1. `CONFUSED`·`MISSED`·`NON_RESPONSE`·`UNMEASURABLE` 네 비율을 계산한다.
2. **헷갈림과 놓침이 각각 20% 를 넘고, 둘의 합이 나머지 두 유형보다 크면** → "함께 높은 경우"
3. 그 외에는 **가장 높은 비율**의 유형을 고른다.
4. 최댓값이 같으면 `CONFUSED` → `MISSED` → `NON_RESPONSE` → `UNMEASURABLE` 순으로 고른다.

각 비율의 분모는 트리거 분모(접속 1분 이상)와 같다 — 팁 문구의 "전체 학생의 N%"도 이 값이다.

> **2번에 "둘의 합" 조건이 붙은 이유**: 조건이 "각각 20% 초과"뿐이면 헷갈림 21%·놓침 21%·무응답 60% 일 때도
> 복합 팁이 떠서 정작 가장 큰 문제(무응답 60%)를 가린다. 복합 팁은 헷갈림과 놓침이 **실제로 지배적일 때만** 뜬다.
> 4번은 비율이 같을 때 팁이 매번 달라지는 것을 막기 위한 결정론적 순서다.

## 12. 미결과 받아들인 위험

### 12.1 여기서 정하지 않은 것

**학습된 ONNX 파일 배포 경로.** 모델 파일은 `.gitignore` 로 제외돼 저장소에 없다.
팀원·CI·배포 서버에 파일이 없으면 판정은 항상 비활성이다. 후보는 Git LFS, 릴리스 아티팩트,
오브젝트 스토리지 + `NEXT_PUBLIC_ATTENTION_ASSET_BASE`, CI 빌드 시 export 다. 한 번도 정한 적이 없다.

**`DETECTOR_UNAVAILABLE` 에서 벗어나는 경로.** §7.1 은 "벗어나면 바로 다시 넣는다"고 했지만
벗어나는 방법을 정의하지 않았다. 모델 로드를 다시 시도하는가, 몇 초 간격으로, 몇 번까지.
다시 시도하지 않으면 사실상 영구 상태다.

**즉시 보고한 뒤 다음 전송 시점.** §4.2 에서 4초 지점에 카메라가 꺼져 즉시 보고했다면
다음 보고는 10초 지점인가 14초 지점인가. 버린 0~4초 구간이 서버 기록에 어떻게 남는지도 정하지 않았다.
서버가 "연속 6건이면 1분"으로 계산하는 방식에 영향을 준다.

**이벤트 스키마의 세부 필드.** `signalQuality` 를 보내는지, 창 구간을 어떻게 표현하는지,
전송이 실패하면 다시 보내는지. 티켓 78 구현을 기준으로 정리해야 한다.

**"수업이 끝날 때까지"라는 상태의 저장 위치.** §5.2 에서 "못 켜요"를 누르면 다시 안 띄우기로 했는데
브라우저 메모리에 두면 새로고침이나 재입장에 사라진다.

### 12.2 알고도 감수한 것

**기기가 느린 학생이 이탈자로 집계된다.**
유효 프레임의 분모를 기대 100장으로 고정했으므로(§3.2), 초당 6장만 처리하는 기기는
얼굴이 완벽하게 잡혀도 60% 가 되어 `UNMEASURABLE` 로 떨어진다.
그 학생은 자세가 멀쩡한데 자세 안내를 받고, 3연속이면 분자에도 들어간다.
프레임 미도착과 얼굴 미검출을 나눠 원인 코드를 붙이는 안이 후보다.
§4.3 의 fps 측정이 이 결정의 관문이다.

**탭 전환으로 집계를 피할 수 있다.**
탭 숨김을 서버에 보내지 않기로 했으므로(§4.3), 다른 탭을 계속 보는 학생이 서버 눈에는 정상으로 보인다.
카메라 토글 회피는 `CAMERA_OFF` 기록이 남지만 탭 전환에는 그 안전장치가 없다.

**오판된 3·4단계가 저참여 카운터를 지운다.**
탭 숨김 중에도 카운터를 계속 세기로 했다(§4.3). 그런데 탭이 숨겨져도 학생은 모니터 앞에 앉아 있고
카메라에는 얼굴이 그대로 잡힌다. 모델은 "정면을 보는 얼굴"로 읽어 3·4단계를 낼 가능성이 높다.
그러면 저참여 카운터가 계속 0으로 되돌아가서 **수업을 안 보는 학생일수록 프롬프트를 덜 받는 역전**이 생긴다.
"탭이 숨겨진 것은 이탈로 확정한다"는 안이 더 정확할 수 있다. §4.3 의 측정을 한 뒤 다시 본다.

**자리에 돌아온 학생이 1분 반 사이에 패널 두 개를 받는다.**
쿨타임을 종류별로 따로 재기로 했다(§5). 방해가 심하다는 의견이 나오면
"어떤 프롬프트든 닫힌 뒤 1분은 다른 것도 안 띄운다"를 한 줄 더하면 된다.

**`OK` 응답을 반복해서 받을 때.** 지금은 응답 종류와 무관하게 쿨타임 5분으로 고정했다.
특정 학생에게 오탐이 몰리면 90분 수업에서 최대 18번까지 같은 질문을 받는다.
쿨타임을 `OK` 가 연속될 때만 늘리는 안(5분 → 15분 → 중단)을 후보로 둔다.
다만 `OK` 는 오탐일 때만 나오지 않는다. 창피해서, 귀찮아서 누르는 학생도 있다.
그런 학생까지 억제하면 정작 도움이 필요한 사람을 놓친다.
