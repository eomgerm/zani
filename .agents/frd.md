## 1. 문서 목적

이 문서는 ZANI MVP에서 사용자가 무엇을 할 수 있어야 하고, 시스템이 각 상황에서 어떻게 동작해야 하는지를 정의한다. 기획, 디자인, 개발, QA가 같은 기준으로 범위와 완료 조건을 이해하는 것이 목적이다.

## 2. 제품 한눈에 보기

ZANI는 실시간 온라인 강의와 수업 후 복습을 연결하는 강의 플랫폼이다.

수업 중에는 학생 브라우저가 시선·머리·상체의 관측 가능한 특징을 10초 단위로 분석해 참여 상태를 판정한다. 학생 카메라 영상은 라이브 WebRTC 수업을 위해 SFU를 통해 다른 참여자에게 전달되지만, 분석 목적으로 별도 전송하거나 녹화하지 않는다. 확인이 필요해 보이는 상태가 이어지면 학생에게 짧은 자기보고 프롬프트를 보여준다. 여러 학생에게 같은 흐름이 나타나면 강사에게 개인 이름이 아닌 집단 팁을 제공하고, 이때 강사의 최근 발화를 전사해 팁 문구에 수업 맥락을 채운다.

수업이 끝나면 강사 카메라, 공유 화면, 전체 음성을 녹화한 자료와 전사, 수업 이벤트, 채팅, 강사 사후 메모를 SSAFY GMS가 분석한다. 강사는 익명 집단 학습 흐름 타임라인과 수업 개선 피드백이 포함된 전체 수업 리포트를 확인한다. 학생은 공통 녹화·전사, 본인의 집중 흐름 타임라인과 근거가 있는 복습 추천을 확인한다.

ZANI는 참여 상태를 약한 신호로만 사용한다. 학생에게 제공하는 `집중 흐름(참고용)`은 측정 가능한 시간 중 양호 상태의 비율을 시간축에 표현한 파생 지표이며, 실제 이해도나 인지 상태를 확정하는 점수가 아니다. 개인별 결과는 성적·출석·징계·순위에 사용하지 않으며 강사에게 공개하지 않는다.

## 3. 목표와 성공 기준

### 3.1 제품 목표

1. 강사가 비대면 수업에서 집단적인 확인 필요 시점을 놓치지 않게 한다.
2. 학생이 수업 흐름을 방해받지 않고 현재 상태를 짧게 표현하게 한다.
3. 수업 녹화, 전사, 이벤트, 강사 메모를 연결해 근거가 있는 복습 후보를 제공한다.
4. 학생 원본 카메라 영상을 서버에 저장하지 않는다.
5. 자동 분석 결과를 개인 평가가 아닌 확인과 복습 지원에만 사용한다.
6. 학생이 본인의 집중 흐름과 복습 근거를 수업 타임라인에서 확인하고 해당 녹화 구간으로 이동하게 한다.
7. 강사가 익명 집단 흐름, 학생 자기보고, 질문, 전사와 수업 이벤트를 함께 보고 수업 개선 후보를 판단하게 한다.

### 3.2 MVP 측정 지표

| 구분 | 지표 | 목표 |
| --- | --- | --- |
| 사용 | 학생 체크 프롬프트 응답률 | 60% 이상 |
| 사용 | 학생 복습 추천 다시 보기 실행률 | 40% 이상 |
| 사용 | 수업 후 리포트 열람률 | 70% 이상 |
| 품질 | 동일 강사 기준 수업당 집단 팁 | 평균 3회 이하 권장 |
| 성능 | 공식 지원 동시 접속 | 30명까지 안정 동작 |
| 성능 | 학생 이벤트 서버 도착 지연 | 3초 이하 |
| 처리 | 실시간 팁 생성 | 트리거 후 15초 이내 |
| 처리 | 전체 사후 결과 생성 | 강사 메모 확정 후 8시간 이내 |

추천 관련성 평가 UI와 분석 동의율 지표는 MVP 범위에서 제외한다.

## 4. MVP 범위

### 4.1 포함

- Google 소셜 로그인과 최초 약관 동의
- 즉시 시작되는 일회성 수업방 생성
- 초대 링크와 참여 코드 입장
- 입장 전 카메라·마이크 테스트
- 실시간 오디오·비디오, 화면 공유, 공개 채팅, 학생-강사 1:1 채팅
- 손들기, 이모지 반응, 참가자 목록, 강사 제어
- 학생 브라우저 내 MediaPipe 특징 추출과 온디바이스 참여도 모델 추론
- 브라우저와 오프라인 학습이 공유하는 `FEATURE_SCHEMA_V1`
- 학생 개인 확인 프롬프트 3종과 강사 집단 팁 5종
- 트리거 시 강사 최근 발화 온디맨드 전사와 팁 문구 생성
- 학생 개인 집중 흐름 타임라인과 익명 집단 학습 흐름 타임라인
- 강사 카메라·공유 화면·전체 음성 녹화
- 종료 후 강사 구간 메모
- SSAFY GMS 전사·멀티모달 분석
- 근거·신뢰도·개선 제안이 포함된 강사 수업 품질 피드백
- 강사 전체 리포트와 학생 개인 복습 추천
- 이메일 완료 알림과 90일 데이터 보관

### 4.2 제외

- 회원가입 시 강사·학생 역할 고정
- 예약 수업, 반복 강좌, 출석부, 과제, 성적 등 LMS 전체 기능
- 기관 SSO, LTI, OneRoster 등 기관 연동
- 학생별 모델 확률, 이해도 확정값, 순위, 등급 및 전체 수업을 단일 값으로 축약한 개인 평가 점수
- 자동 출석·성적·징계 판단
- 퀴즈 기능과 Knowledge Tracing
- 학생 카메라 원본 녹화·서버 분석
- 학생 간 1:1 채팅
- 학생별 자동 분석 결과를 강사에게 공개하는 기능
- 모바일·태블릿과 Chrome 이외 브라우저의 공식 지원
- 복습 추천 관련성 평가 UI
- 강사 사후 메모 확정 후 수정·재생성
- 객체 저장소(S3) 사용 — 녹화·산출물은 EC2 로컬 저장소에 둔다

## 5. 사용자와 역할

### 5.1 전역 계정

모든 사용자는 같은 형태의 계정을 사용한다. 계정에 강사 또는 학생 역할을 영구 저장하지 않는다.

### 5.2 수업방 역할

- 방을 만든 사용자는 해당 방의 `강사`가 된다.
- 초대 링크나 참여 코드로 들어온 사용자는 해당 방의 `학생`이 된다.
- 한 사용자는 어떤 방에서는 강사이고 다른 방에서는 학생일 수 있다.

| ID | 요구사항 |
| --- | --- |
| ROLE-001 | 시스템은 사용자 역할을 수업방 참여 관계에 저장해야 한다. |
| ROLE-002 | 방 생성자만 해당 방의 강사 권한을 가져야 한다. |
| ROLE-003 | MVP는 공동강사·조교 승격 기능을 제공하지 않아야 한다. |
| ROLE-004 | 역할은 LiveKit 토큰 `metadata`로 전달하고 클라이언트가 임의로 정하지 않아야 한다. |

## 6. 전체 사용자 여정

### 6.1 강사 여정

1. Google 계정으로 로그인하고 최초 약관에 동의한다.
2. 수업 제목을 입력하고 방을 만든다.
3. 방이 생성되는 즉시 수업 시간과 녹화가 시작된다.
4. 초대 링크나 참여 코드를 학생에게 전달한다.
5. 실시간 강의를 진행하고 집단 팁을 확인한다.
6. 필요하면 학생을 음소거·퇴장시키거나 화면 공유 권한을 제어한다.
7. `수업 종료` 버튼을 누르거나, 3시간이 지나 자동 종료된다.
8. 녹화 구간을 선택해 사후 메모를 한 번 작성하거나 메모 없이 완료한다.
9. 이메일을 받은 뒤 익명 집단 타임라인과 수업 개선 피드백이 포함된 전체 리포트를 확인한다.

### 6.2 학생 여정

1. Google 계정으로 로그인하고 최초 약관에 동의한다.
2. 초대 링크나 참여 코드를 입력한다.
3. 카메라·마이크 테스트를 모두 통과한다.
4. 진행 중인 수업에 즉시 입장한다.
5. 수업 중 채팅, 손들기, 이모지 반응을 사용하고 확인 프롬프트에 응답한다.
6. 이메일을 받은 뒤 공통 녹화·전사, 본인 집중 흐름 타임라인과 복습 추천을 확인한다.

## 7. 계정·약관·로그인

### 7.1 Google 로그인

- 로그인 수단은 Google OAuth만 제공한다.
- 최초 로그인 시 Google 계정의 고유 식별자, 표시 이름, 이메일, 프로필 이미지를 계정에 연결한다.
- 이메일·비밀번호 회원가입과 비밀번호 재설정은 제공하지 않는다.
- Access Token은 `Authorization: Bearer` 헤더로 전달하고 유효기간은 1시간이다. Refresh Token은 HttpOnly 쿠키로만 오가며 재발급마다 회전한다.

### 7.2 최초 필수 약관

최초 로그인 사용자는 다음 내용을 포함한 필수 약관에 동의해야 계정을 생성할 수 있다.

- 강사 카메라, 현재 공유 화면, 전체 참여자 음성 녹화
- 수업 전사, 요약, 복습 추천을 위한 데이터 처리
- 학생 브라우저의 시선·머리·상체 특징 분석
- 참여 상태 이벤트, 개인 집중 흐름 파생값, 확인 응답, 채팅, 접속 기록 저장
- SSAFY GMS 분석을 위한 가명화 데이터 처리
- 90일 기본 보관과 강사 수동 삭제

수업 입장 시에는 별도 동의 버튼을 다시 받지 않지만, 현재 수업이 녹화·분석된다는 사실을 명확히 고지한다.

> 필수 분석 동의 정책과 약관 문구는 파일럿 전 개인정보·법률 검토를 거쳐야 한다.

| ID | 요구사항 |
| --- | --- |
| AUTH-001 | 사용자는 Google OAuth로 로그인·로그아웃할 수 있어야 한다. |
| AUTH-002 | 최초 약관에 동의하지 않은 사용자는 계정을 생성하거나 서비스에 진입할 수 없어야 한다. |
| AUTH-003 | 약관 버전, 동의 시각, 사용자 ID를 저장해야 한다. |
| AUTH-004 | 인증이 만료된 이메일 링크는 로그인 후 원래 권한 확인 화면으로 돌아와야 한다. |
| AUTH-005 | 모든 보호 API는 Bearer 헤더로만 인증하고 쿠키는 Refresh 전용으로 사용해야 한다. |

## 8. 수업방 생성·입장·상태

### 8.1 방 생성

- 강사는 제목을 입력하고 방을 생성한다. 예약 일시나 반복 일정은 받지 않는다.
- 생성 즉시 상태는 `LIVE`가 되고 수업 시간과 녹화가 시작된다.
- 한 계정은 동시에 하나의 `LIVE` 방만 만들 수 있다.
- 강사 카메라를 사용할 수 없으면 제한 모드로 시작할 수 있다. 제한 모드에서는 화면 공유와 음성을 녹화하고 강사 비언어 분석만 제외한다.

### 8.2 초대와 입장

- 시스템은 초대 링크와 8자리 참여 코드를 함께 발급한다.
- 학생은 유효한 링크·코드로 접속하면 강사 승인 없이 입장한다. 같은 코드로 다시 입장해도 참가자를 새로 만들지 않는다(멱등).
- 방 생성 이후 언제든 늦게 입장할 수 있다.
- 방에 한 번 입장한 순간 사후 자료 접근 자격을 얻는다.
- 강제 퇴장은 현재 연결만 종료한다. 학생은 같은 링크·코드로 다시 입장할 수 있고 사후 권한도 유지한다.

### 8.3 수업 시간과 인원

- 최대 진행 시간은 3시간이다. 종료 예정 시각은 `시작 시각 + 3시간`이며 강의실 진입 응답으로 전달한다.
- 자동 종료 10분 전부터 강사·학생 화면에 남은 시간을 안내한다.
- 3시간이 되면 서버 스케줄러가 수업을 자동 종료한다.
- 강사는 언제든 `수업 종료`를 눌러 직접 종료할 수 있다.
- 제품은 입장 인원 하드 캡을 두지 않는다. 동시 30명까지 공식 성능 보장 대상으로 삼는다.

### 8.4 종료 경로

종료는 세 경로에서 발생하며 모두 같은 처리를 거친다. 이미 종료된 수업에 대한 종료 요청은 오류가 아니라 현재 상태를 돌려준다(멱등).

| 경로 | 사유 | 판단 주체 |
| --- | --- | --- |
| 강사 명시 종료 | `INSTRUCTOR_REQUEST` | 강사 요청 |
| 최대 시간 도달 | `MAX_DURATION_REACHED` | 서버 스케줄러(1분 주기) |
| 강사 미복귀 | `INSTRUCTOR_ABSENT` | presence 5분 유예 만료 |

### 8.5 상태 전이

```
방 생성 요청
→ LIVE
→ ENDED
→ 강사 메모 대기
→ 전사·AI 분석 중
→ 완료 또는 분석 실패
→ 90일 만료 또는 강사 삭제
→ 삭제됨
```

| ID | 요구사항 |
| --- | --- |
| ROOM-001 | 방 생성 성공과 동시에 수업 시작 시각과 녹화 시작 시각을 기록해야 한다. |
| ROOM-002 | 진행 중 방이 있는 사용자의 새 방 생성 요청을 차단해야 한다. |
| ROOM-003 | 초대 링크와 참여 코드는 방 종료 전까지만 라이브 입장에 사용할 수 있어야 한다. |
| ROOM-004 | 유효한 초대 정보와 로그인 계정을 가진 학생은 승인 없이 입장해야 한다. |
| ROOM-005 | 방은 3시간에 자동 종료되어야 하고 10분 전 안내를 표시해야 한다. |
| ROOM-006 | 30명 이하에서는 입장·미디어·이벤트·채팅 기능이 안정적으로 동작해야 한다. |
| ROOM-007 | 세 종료 경로는 하나의 종료 처리를 공유하고 중복 종료에 멱등해야 한다. |
| ROOM-008 | 수업을 연 강사만 명시 종료를 호출할 수 있어야 한다. |

## 9. 입장 전 기기 테스트

학생은 수업방에 들어가기 전에 다음을 모두 통과해야 한다.

1. 공식 지원 환경 확인: Windows 또는 macOS의 최신 데스크톱 Chrome
2. 카메라 권한과 실제 영상 입력 확인
3. 마이크 권한과 입력 레벨 확인
4. 선택한 카메라·마이크 미리 보기
5. 현재 수업의 녹화·분석 고지 확인

카메라 또는 마이크 테스트가 실패하면 입장할 수 없다. 시스템은 권한 거부, 장치 없음, 다른 앱에서 사용 중, 지원하지 않는 브라우저를 구분해 해결 방법을 안내한다. 점검에서 고른 장치는 강의실에서 그대로 이어 쓴다.

| --- | --- |
| DEVICE-001 | 학생은 카메라와 마이크 테스트를 모두 통과해야 입장할 수 있어야 한다. |
| DEVICE-002 | 지원하지 않는 브라우저·기기에서는 입장 대신 지원 환경 안내를 표시해야 한다. |

## 10. 실시간 강의실

### 10.1 오디오·비디오

- 모든 참여자는 자신의 마이크와 카메라를 켜고 끌 수 있다. 토글은 실제 트랙 publish 상태를 바꾼다.
- 학생 카메라 영상은 라이브 전송에는 사용하지만 녹화물에는 포함하지 않는다.
- 강사 카메라 영상은 녹화와 강사 비언어 강조 구간 분석에 사용한다.
- 강사 카메라가 수업 도중 사용할 수 없게 되면 제한 모드로 전환하고 강사에게 상태를 알린다.
- 서버가 특정 source의 publish 권한을 회수하면(강사 제한 모드) 해당 장치 조작을 막고 제한 상태를 화면에 표시한다.

### 10.2 화면 공유

- 강사는 기본 화면 공유 권한을 가진다.
- 학생은 강사의 승인을 받은 동안만 화면을 공유할 수 있다.
- 한 번에 하나의 공유 화면만 활성화할 수 있다.
- 강사는 학생의 화면 공유를 언제든 중지할 수 있다.
- 현재 활성화된 공유 화면은 강사 카메라·전체 음성과 함께 녹화한다.

### 10.3 채팅

- 공개 채팅은 현재 참여자 모두에게 보인다.
- 학생은 강사에게만 보이는 1:1 메시지를 보낼 수 있다. 학생 간 1:1 메시지는 제공하지 않는다.
- 공개 채팅은 공통 질문·채팅 요약에 사용한다.
- 학생-강사 1:1 메시지는 해당 학생의 개인 추천과 강사 리포트에만 사용한다.

### 10.4 손들기·이모지·참가자 목록

- 학생은 손들기 상태를 켜고 끌 수 있고, 강사는 순서를 확인하고 내릴 수 있다.
- 이모지 반응은 모든 참여자에게 일시적으로 표시한다.
- 참가자 목록에는 표시 이름, 마이크·카메라·손들기·화면공유 상태를 표시한다.
- 채팅·이모지·손들기가 없다는 사실 자체는 확인 필요 신호로 사용하지 않는다.

### 10.5 강사 제어

- 강사는 학생 마이크를 음소거할 수 있고, 강제로 켤 수는 없다.
- 강사는 학생을 현재 연결에서 즉시 퇴장시킬 수 있다. 퇴장된 학생의 재입장과 사후 접근은 차단하지 않는다.
- 강사는 학생 화면 공유를 중지할 수 있다.

### 10.6 연결 상태와 presence

- 모든 참여자는 접속 중 서버에 10초 주기로 presence heartbeat를 보낸다. 서버는 Redis TTL 30초로 접속 여부를 관리한다.
- heartbeat에는 연결 상태(`CONNECTED`·`RECONNECTING`·`DISCONNECTED`)를 함께 보낸다.
- 학생 연결이 끊기면 자동 재연결을 시도하고, 실패하면 재입장 화면을 제공한다.
- 재연결·재입장 구간은 분석 자체가 불가능하므로 참여 상태를 만들지 않는다(§11.6의 이름 구분 참조).
- 강사 연결이 비정상적으로 끊기면 5분 유예를 시작하고, 유예가 지난 뒤 도착한 heartbeat가 수업을 종료시킨다. 학생 화면에는 유예 중임과 종료 사실을 안내한다.

| ID | 요구사항 |
| --- | --- |
| LIVE-001 | 시스템은 동시 오디오·비디오 송수신을 지원해야 한다. |
| LIVE-002 | 시스템은 강사 승인 기반 학생 화면 공유와 단일 활성 공유를 보장해야 한다. |
| LIVE-003 | 공개 채팅과 학생-강사 1:1 채팅의 열람 범위를 분리해야 한다. |
| LIVE-004 | 시스템은 손들기, 이모지, 참가자 상태를 실시간 동기화해야 한다. |
| LIVE-005 | 강사는 학생 음소거·퇴장·공유 중지를 수행할 수 있어야 한다. |
| LIVE-006 | 강사 비정상 이탈 후 5분 유예와 자동 종료가 동작해야 한다. |
| LIVE-007 | 미디어 토글은 로컬 화면 상태가 아니라 실제 publish 상태를 반영해야 한다. |
| LIVE-008 | presence heartbeat 주기는 서버 TTL보다 충분히 짧아야 한다. |

## 11. 학생 카메라 분석과 참여 상태

### 11.1 처리 원칙

- MediaPipe Face Landmarker와 Pose Landmarker 기반 특징 추출, 그리고 참여도 모델 추론은 학생 브라우저에서 실행한다.
- 얼굴 분석 목표 주기는 초당 10프레임이며 측정 가능 최소 기준은 초당 5프레임이다. 상체 자세 분석 목표 주기는 초당 5프레임이다.
- 학생 원본 프레임과 랜드마크 원본을 분석 API로 보내거나 영구 저장하지 않는다.
- 서버에는 **10초 단위 판정 결과와 프롬프트 응답만** 전송한다.
- 분석은 이해도를 확정하는 수단이 아니라 확인 질문, 개인 집중 흐름, 복습 후보와 익명 집단 피드백을 만들기 위한 약한 신호다.

### 11.2 공통 특징 스키마

룰 폴백과 참여도 모델은 동일한 `FEATURE_SCHEMA_V1`을 사용한다. 연속형 기본 특징 51개(머리·얼굴 6, 시선 대체 6, 눈 개방도 2, Blendshape 31, 상체 6)의 1초 평균·표준편차 102개에 품질·맥락 6개(얼굴·홍채·자세 유효 비율, 실제 FPS, 탭 활성 비율, 카메라 ON 비율)를 더해 1초 108차원을 만든다. 모델 입력은 최근 10초를 묶은 `10 × 108` 텐서다.

브라우저와 오프라인 학습 전처리는 같은 MediaPipe 모델 파일, 특징 계산식, 정규화 방식, 스키마 버전을 사용해야 한다. `탭 활성 비율`과 `카메라 ON 비율`은 EngageNet에 없는 서비스 맥락값이라 초기 시각 모델에서는 입력 마스크로 제외한다.

### 11.3 개인 기준선

- 카메라 분석이 시작되면 측정 가능한 표본 약 20초로 개인 기준선을 만든다.
- 초기 20초 중 유효 표본이 부족하면 기준선 확정을 미룬다.
- 머리·시선·눈 개방도·상체 특징은 절대값이 아니라 개인 기준선 대비 변화량·비율을 사용한다.
- 기준선은 이상치 영향을 줄이기 위해 중앙값과 IQR을 사용한다.

### 11.4 참여도 모델과 10초 판정

- 모델은 4단계를 출력한다: `Not-Engaged`(1) · `Barely-Engaged`(2) · `Engaged`(3) · `Highly-Engaged`(4)
- 판정 단위는 **10초**다. 10초마다 판정 1건을 만든다.
- **3·4단계** → 그 학생은 `GOOD`이며 프롬프트를 띄우지 않는다.
- **1·2단계가 3연속(30초)** → 이해 확인 프롬프트를 띄운다.
- **얼굴 판단 불가가 3연속(30초)** → `UNMEASURABLE`로 확정하고 자세 안내 프롬프트를 띄운다.
- 연속 카운터는 다른 결과가 나오면 0으로 되돌린다.
- 모델 추론이 실패하면 룰 폴백으로 전환하고 실패를 기록한다. 폴백 중에도 출력 계약과 10초 판정 단위는 동일하다.

### 11.5 학생 상태 6가지

| 상태 | 확정 조건 | 프롬프트 | 집단 트리거 분자 | 집단 트리거 분모 |
| --- | --- | --- | --- | --- |
| `GOOD` | 모델 3·4단계, 또는 프롬프트에 "이해했어요" | — | ✕ | 포함 |
| `CONFUSED` | 1·2단계 3연속 후 "헷갈려요" | 이해 확인 | ○ | 포함 |
| `MISSED` | 1·2단계 3연속 후 "놓쳤어요" | 이해 확인 | ○ | 포함 |
| `NON_RESPONSE` | 1·2단계 3연속 후 30초 무응답 | 이해 확인 | ○ | 포함 |
| `UNMEASURABLE` | 얼굴 판단 불가 3연속 | 자세 안내 | ○ | 포함 |
| `CAMERA_OFF` | 입장 후 카메라 트랙 OFF | 카메라 확인 | ✕ | "예" 응답 시 제외 |

상태 표기는 언더스코어로 통일한다(`NON_RESPONSE`, `CAMERA_OFF`).

### 11.6 두 종류의 UNMEASURABLE

| 구분 | 원인 | 프롬프트 | 트리거 분자 |
| --- | --- | --- | --- |
| 연결 불가 | LiveKit 재연결·재입장 | 없음 | ✕ (분석 자체가 불가) |
| 판정 UNMEASURABLE | 화면 이탈·얼굴 미검출 | 자세 안내 | ○ |

구현에서 이름을 분리한다. 연결 쪽은 신호 가용성(`signalAvailability`), 판정 쪽은 참여 상태(`AttentionState.UNMEASURABLE`)로 쓴다.

### 11.7 학생에게 보이는 실시간 상태

실시간 강의실에서는 학생에게 단계·점수·세부 수치를 표시하지 않는다. 표시하는 것은 `분석 중`, `카메라 OFF`, `측정 불가` 세 가지뿐이다. 수업 후 학생 리포트에서만 본인의 `집중 흐름(참고용)`을 제공한다.

### 11.8 판정 엔진 계약

- 판정 시작·종료 시각(10초 구간)
- 참여 상태 6종 중 하나
- 근거 코드 목록과 신호 품질 요약
- `featureSchemaVersion`
- `engineType`: `MODEL` 또는 `RULE`
- `engineVersion`

ZANI 특징 집계값을 모델 재학습에 사용하려면 일반 운영 저장과 분리된 연구 참여 동의를 받아야 한다.

| ID | 요구사항 |
| --- | --- |
| ANALYSIS-001 | 학생 영상 특징 추출과 모델 추론은 브라우저 안에서만 수행해야 한다. |
| ANALYSIS-002 | 원본 프레임과 랜드마크 원본을 저장하거나 분석 API로 전송하지 않아야 한다. |
| ANALYSIS-003 | 얼굴 판단 불가는 다른 상태로 변환하지 않고 `UNMEASURABLE`로 처리해야 한다. |
| ANALYSIS-004 | 실시간 학생 UI는 분석 작동 상태만 표시하고 개인 판정을 노출하지 않아야 한다. |
| ANALYSIS-005 | 판정 단위는 10초이고, 상태 확정은 3연속 규칙을 따라야 한다. |
| ANALYSIS-006 | `FEATURE_SCHEMA_V1`은 1초 108차원, 10초 `10 × 108` 형식으로 버전 관리되어야 한다. |
| ANALYSIS-007 | 브라우저와 오프라인 학습 전처리는 동일한 특징 계산식과 MediaPipe 모델 버전을 사용해야 한다. |
| ANALYSIS-008 | 모델 추론 실패 시 룰 폴백으로 전환하고 출력 계약을 유지해야 한다. |
| ANALYSIS-009 | 연결 불가와 판정 UNMEASURABLE을 서로 다른 개념으로 구분해야 한다. |
| ANALYSIS-010 | 일반 운영에서는 프레임별 특징과 1초·10초 입력 텐서를 서버에 영구 저장하지 않아야 한다. |
| ANALYSIS-011 | 연구·재학습용 특징 저장에는 별도 동의와 논리적 분리를 적용해야 한다. |

## 12. 학생 확인 프롬프트

### 12.1 프롬프트 3종

| 종류 | 발동 | 선택지 | 노출 | 쿨타임 |
| --- | --- | --- | --- | --- |
| 이해 확인 | 1·2단계 3연속 | 이해했어요 / 헷갈려요 / 놓쳤어요 | 30초 | 5분 |
| 자세 안내 | UNMEASURABLE 3연속 | 확인 | 30초 | 무시 |
| 카메라 확인 | 카메라 OFF 감지 | 예 / 아니오 | 30초 | 1회 한정 |

- 자세 안내 문구: "카메라에 얼굴이 나오도록 조정해주세요"
- 카메라 확인 문구: "카메라 연결이 어려운 상태인가요?"

### 12.2 동작 규칙

- 프롬프트는 강의 내용을 가리는 전체 화면 모달이 아닌 하단 패널로 표시한다.
- 30초 안에 응답하지 않으면 자동으로 닫는다. **이해 확인**만 무응답이 상태로 남는다(`NON_RESPONSE`).
- 같은 학생에게 이해 확인 프롬프트를 다시 띄우려면 이전 표시 시각으로부터 **5분**이 지나야 한다.
- **자세 안내는 쿨타임을 무시**한다. 화면에서 이탈한 상태는 즉시 알리는 것이 목적이다.
- 카메라 확인에 **"예"**로 답하면 이후 같은 수업에서 다시 묻지 않고, 그 학생을 집단 비율 분모에서 제외한다. 카메라를 다시 켜면 분모에 복귀한다.
- "이해했어요"는 해당 구간의 개인 추천 우선순위를 낮추는 근거다.
- "헷갈려요"·"놓쳤어요"는 집단 팁과 개인 추천의 강한 근거다.
- `NON_RESPONSE`는 단독으로 이해도 라벨로 사용하지 않는다.

## 13. 강사 집단 팁

### 13.1 개인정보 원칙

- 강사는 학생별 자동 분석 상태와 학생별 응답을 볼 수 없다.
- 강사는 최근 구간의 전체 비율, 응답 분포, 팁 유형만 본다.
- 학생별 데이터는 해당 학생의 개인 복습 추천에만 사용한다.

### 13.2 분모·분자와 발동

- **분모**: 연속 접속 1분을 넘긴 학생. 카메라 확인에 "예"로 답한 학생은 제외한다.
- **분자**: 최근 5분 안에 `CONFUSED`·`MISSED`·`NON_RESPONSE`·`UNMEASURABLE`이 한 번이라도 있었던 고유 학생.
- **발동**: 분자 / 분모 ≥ **30%**
- **쿨타임**: 팁 1회 발송 후 **10분**. 팁 유형과 무관하며 트리거 발생 시각을 기준으로 센다.
- 측정 가능 학생 비율에 대한 전제 조건은 두지 않는다.

### 13.3 슬라이딩 윈도우

10초 버킷 30개로 5분을 유지한다. 새 10초가 들어오면 가장 오래된 10초를 버린다. 판정 시점은 학생이 프롬프트에 응답한 시각이다.

### 13.4 팁 유형 선택

1. `CONFUSED`·`MISSED`·`NON_RESPONSE`·`UNMEASURABLE` 네 비율을 계산한다(분모는 §13.2와 같다).
2. 헷갈림과 놓침이 **각각 20%를 넘으면** "함께 높은 경우"를 고른다.
3. 그 외에는 가장 높은 비율의 유형을 고른다.

### 13.5 팁 문구 5종

| 유형 | 제목 | 본문 | 제안 |
| --- | --- | --- | --- |
| 헷갈림 | 추가 설명이 필요해요 | 전체 학생의 N%가 현재 내용을 헷갈려 하고 있어요. | {핵심 개념}을 다른 예시로 다시 설명해 주세요. |
| 놓침 | 내용을 다시 짚어주세요 | 전체 학생의 N%가 방금 설명을 놓쳤어요. | {핵심 내용}을 짧게 요약한 뒤 수업을 이어가 주세요. |
| 헷갈림+놓침 | 수업 흐름을 점검해 주세요 | 전체 학생의 N%가 현재 수업을 따라가는 데 어려움을 겪고 있어요. (헷갈려요 N% · 놓쳤어요 N%) | 설명 속도를 낮추고 {핵심 내용}을 다시 정리해 주세요. |
| 무응답 | 학생 반응을 확인해 주세요 | 전체 학생의 N%가 질문에 응답하지 않았어요. | 간단한 질문을 통해 학생들의 참여 상태를 확인해 주세요. |
| UNMEASURABLE | 학생들이 자리를 비운 것 같아요 | 전체 학생의 N%가 현재 화면에서 감지되지 않고 있어요. | 간단한 질문을 통해 학생들의 참여 상태를 확인해 주세요. |

`{핵심 개념}`·`{핵심 내용}`은 온디맨드 전사 결과로 채운다(§14).

## 14. 실시간 온디맨드 전사

### 14.1 오디오 버퍼

- 강사 브라우저는 자신의 마이크 트랙을 복제해 최근 **300초**를 링버퍼로 유지한다.
- 트리거가 발생하면 서버 요청에 따라 **링버퍼 전체**를 업로드한다.
- 강사 마이크가 꺼져 있으면 업로드하지 않는다.

### 14.2 전사와 팁 생성

- 전사는 SSAFY GMS `whisper-1`을 사용하고 timeout 10초, 재시도 없음으로 호출한다.
- 전사 결과를 LLM에 넘겨 `{핵심 개념}`·`{핵심 내용}`을 채운 팁 JSON을 만든다. 허용된 액션 스키마를 벗어난 응답은 폐기한다.
- 오디오 원본은 전사 직후 폐기한다.

## 15. 녹화

### 15.1 녹화 범위

- 강사 카메라 영상
- 현재 활성화된 강사 또는 승인 학생의 공유 화면
- 강사와 학생의 전체 발화 음성
- 학생 발화자를 식별할 수 있는 오디오 트랙 메타데이터

학생 카메라 영상은 녹화에서 제외한다. 공유 화면이 없으면 강사 카메라를 주 화면으로, 공유 화면이 있으면 공유 화면을 주 화면으로 하고 강사 카메라를 보조 화면으로 합성한다.

### 15.2 저장과 처리

- 녹화는 LiveKit Track Egress로 참가자·트랙별 원본을 만들고, 수업 종료 후 시간축을 정렬해 최종 MP4로 병합한다.
- 저장소는 **EC2 로컬 디스크**다. S3는 사용하지 않는다.
- 녹화 산출물의 참가자 식별자는 익명 별칭(`instructor`, `student-001`)만 사용한다. 실명·이메일·내부 ID를 경로나 manifest에 넣지 않는다.
- 학생 카메라는 Egress 요청 자체를 생성하지 않는다.
- Egress 시작은 outbox로 기록한 뒤 릴레이가 수행하며, 중복 시작을 세 겹으로 막는다(dedup key, claim, 기존 Egress 채택).

### 15.3 녹화 상태

- 녹화 중임을 모든 참여자에게 항상 표시한다.
- Egress가 실패하면 강사에게 표시하고 지수 백오프로 재시도한다. 상한을 넘기면 실패로 남긴다.
- 녹화가 완전하지 않으면 처리 상태와 운영 로그에 누락 구간과 사유를 기록하고 가능한 데이터만 분석한다.

## 17. 사후 전사·멀티모달 AI 분석

### 17.1 처리 순서

```
강사 메모 확정
→ 녹화 파일 무결성 확인
→ 오디오 추출과 전사
→ 전사 화자·타임스탬프 정렬
→ 자막 기반 개념 구간 분할과 질문 연결
→ 10~15분 영상 청크 생성
→ 사용자 메타데이터 가명화
→ SSAFY GMS 멀티모달 분석
→ 구조화 결과 자동 근거 검증
→ 개인·집단 타임라인과 수업 품질 피드백 생성
→ 공통·강사·학생 결과 조립
→ 권한별 공개
→ 완료 이메일 발송
```

### 17.2 전사

- 전사는 시작·종료 시각, 발화 텍스트, 화자 식별자, 신뢰도를 가져야 한다.
- 공통 전사 UI에는 참여자의 실제 표시 이름을 보여준다.
- 지원 언어의 우선순위는 한국어다.
- 실행 환경은 §28 TBD-01에서 확정한다.

### 17.3 GMS 입력과 가명화

10~15분 단위 녹화 청크, 가명화된 화자 식별자가 포함된 전사, 학생별 가명화 이벤트와 응답, 집단 반응 이벤트, 공개 채팅, 허용된 1:1 채팅, 확정된 강사 메모를 보낸다. 이름·이메일·Google 식별자·내부 사용자 ID는 보내지 않는다. 영상 속 얼굴·음성처럼 미디어 자체에 포함된 정보는 완전 익명화가 불가능하므로 이 처리를 `메타데이터 가명화`로 정의한다.

### 17.4 비언어 정보 활용

강사의 손짓·가리키기·큰 동작을 강조 구간의 보조 신호로만 사용한다. 강사의 감정·성격·역량을 평가하지 않는다. 학생 카메라 영상은 사후 분석 입력에 포함하지 않는다.

### 17.5 구조화 출력과 자동 검증

각 결과 항목은 녹화 시각, 전사 청크 ID, 이벤트 ID, 메모 ID, 개념 구간 ID, 추천 개념명·요약·이유, 피드백 유형·신뢰도·근거·제안을 구조화해 반환한다. 시스템은 시각이 실제 녹화 범위 안인지, ID가 같은 수업의 것인지 검사하고 실패한 항목만 제거한다.

### 17.6 개념 구간과 질문 연결

- 전사와 화면 내용으로 개념별 대표 설명 구간의 시작·종료 시각을 만든다.
- 질문 작성 시각과 질문이 대상으로 하는 개념 설명 구간을 서로 다른 값으로 저장한다.
- 신뢰도가 낮으면 질문 시점 전후 60초를 임시 구간으로 사용하고 자동 연결임을 표시한다.
- 복습 링크는 질문 시각이 아니라 개념 설명 구간의 시작 시각으로 이동한다.

### 17.7 수업 품질 피드백 원칙

- 학생 카메라 신호 하나로 생성하지 않고 익명 집단 흐름, 자기보고, 질문, 전사, 개념 경계, 발화 속도, 공개 상호작용과 강사 메모를 결합한다.
- 개념 명확성, 수업 속도·정보량, 상호작용 효과, 개념 전환, 흐름 회복, 잘된 설명 방식으로 구분한다.
- 각 피드백은 구간, 근거, `높음·중간·낮음` 신뢰도, 제안, 녹화 링크를 가진다.
- 낮은 신뢰도는 평가가 아닌 `검토 후보`로 표현하고, 수업 전체를 단일 점수로 축약하지 않는다.

| AI-002 | GMS 전송 전에 직접 식별 메타데이터를 가명화해야 한다. |
| AI-003 | 강사 비언어 정보는 강조 구간 보조 신호로만 사용해야 한다. |

| AI-007 | 질문 작성 시각과 개념 설명 구간을 분리해 저장해야 한다. |

| AI-009 | 수업 품질 피드백은 구간·근거·신뢰도·제안과 녹화 링크를 포함해야 한다. |

## 18. 강사 리포트

### 18.1 공통 수업 자료

수업 기본 정보와 실제 시간, 참여자 수, 전체 녹화와 실명 화자 전사, 시간대별 요약·챕터·핵심 개념, 공개 질문·채팅 요약, 강사에게 온 1:1 질문과 연결된 개념 구간, 강사 메모와 AI가 연결한 강조 구간을 제공한다.

### 18.2 익명 집단 학습 흐름 타임라인

수업 시간축에 맞춰 5초마다 다음 값을 계산한다.

```
확인 필요 학생 비율(t)
= 최근 30초에 CONFUSED·MISSED·NON_RESPONSE·UNMEASURABLE 이 발생한 집계 대상 고유 학생 수
  ÷ 해당 시점의 집계 대상 학생 수
```

- 집계 대상은 해당 시점에 연결되어 있고 연속 접속 1분이 지난 학생이다.
- 카메라 확인에 "예"로 답한 학생은 분모에서 제외하고, 카메라 OFF 학생 비율을 별도 계열로 제공한다.
- 집계 대상이 5명 미만이면 비율을 숨기고 `집계 인원이 부족합니다`로 표시한다.
- 같은 시간축에 측정 가능 비율, 응답 분포, 질문 밀도, 개념·챕터 구간, 흐트러짐 구간, 상호작용 시점, 집단 팁과 메모 시점을 정렬한다.
- 그래프·구간을 클릭하면 관련 녹화 시각으로 이동한다.

### 18.3 집중 흐트러짐 동적 구간

- 확인 필요 비율이 30% 이상으로 20초 지속되면 시작한다.
- 20% 미만으로 30초 유지되면 종료한다.
- 두 구간 간격이 15초 미만이면 병합한다.
- 경계 15초 이내에 개념·챕터·문장 경계가 있으면 그 경계로 보정한다.
- 임계값은 원격 설정으로 조정할 수 있어야 한다.

### 18.4 수업 품질 피드백

개념 명확성, 수업 속도·정보량, 상호작용 효과, 개념 전환, 흐름 회복, 잘된 설명 방식 차원으로 제공하며, 각 카드는 관련 개념과 시각, 녹화 링크, 익명 집계 근거, 신뢰도, 구체적 제안을 포함한다. 전체 수업에 단일 품질 점수나 등급을 부여하지 않는다.

### 18.5 개인정보 원칙

강사는 학생별 자동 분석 상태·응답·집중 흐름·복습 추천을 볼 수 없고, 익명 그래프에서 개인 목록으로 가는 드릴다운도 제공하지 않는다.

| ID | 요구사항 |
| --- | --- |
| REPORT-I-001 | 강사에게 전체 녹화·전사·집계 리포트를 제공해야 한다. |
| REPORT-I-002 | 강사 리포트에 학생별 신호·응답·개인 추천을 노출하지 않아야 한다. |

## 19. 학생 리포트와 복습 추천

### 19.1 공통 자료

실제 입장 기록이 있는 학생은 녹화, 실명 화자 전사, 시간대별 요약, 공통 핵심 개념, 공개 질문·채팅 요약을 볼 수 있다. 다른 학생의 1:1 메시지는 볼 수 없다.

### 19.2 개인 집중 흐름 타임라인

```
집중 흐름(t)
= 최근 30초 중 GOOD 으로 판정된 측정 가능 시간
  ÷ 최근 30초의 전체 측정 가능 시간
  × 100
```

- 5초마다 값을 제공한다.
- 최근 30초의 측정 가능 시간이 70% 미만이면 값을 계산하지 않고 회색 공백으로 표시한다.
- `CAMERA_OFF`와 `UNMEASURABLE`은 0점으로 표시하지 않는다.
- 하단 상태 막대로 확인 필요 구간, 카메라 OFF, 측정 불가를 구분한다.
- 확인 프롬프트, 질문, 중요 개념, 복습 구간을 같은 시간축에 표시하고 클릭 시 녹화로 이동한다.
- 색상만으로 구분하지 않고 텍스트·아이콘·패턴을 함께 사용한다.
- 전체 평균 점수로 축약하거나 다른 학생과 비교하지 않는다.

### 19.3 개인 복습 추천

근거가 있는 경우에만 0~5개 제공하며, 각 추천은 개념명, 구간 시각, 이유, 복습 포인트, 다시 보기 링크, 관련 질문, 사용 근거 유형을 가진다.

우선순위는 ① "헷갈려요"·"놓쳤어요"로 응답한 개념 구간 ② 질문한 개념 구간 ③ `NON_RESPONSE`와 반복된 확인 필요 상태가 함께 있는 구간 ④ 중요 개념에서 확인 필요 상태가 반복된 구간이다. 단일 이벤트만으로는 추천을 만들지 않는다. "이해했어요"는 우선순위를 낮춘다.

| ID | 요구사항 |
| --- | --- |
| REPORT-S-001 | 실제 입장 기록이 있는 학생에게 공통 녹화·전사를 제공해야 한다. |
| REPORT-S-002 | 학생에게 본인 데이터로 생성된 추천만 0~5개 제공해야 한다. |
| REPORT-S-003 | 추천은 검증된 구간과 이유를 함께 표시해야 한다. |
| REPORT-S-004 | 다시 보기 링크는 개념 설명 시작 시각으로 이동해야 한다. |
| REPORT-S-005 | 개인 근거가 없으면 추천 0개 상태를 명확히 표시해야 한다. |
| REPORT-S-006 | 집중 흐름은 30초 이동창 기준으로 5초 간격 제공해야 한다. |

| REPORT-S-009 | 단일 이벤트만으로 복습 추천을 생성하지 않아야 한다. |

## 26. 시스템 구성 원칙

- 프론트엔드: Next.js
- 백엔드: Spring Boot (Java 21)
- 데이터베이스: MySQL, 마이그레이션은 Flyway 전진 전용
- 실시간 집계·잠금·큐: Redis
- 미디어: 자체 구축 LiveKit SFU, coturn, LiveKit Track Egress
- 저장소: **EC2 로컬 디스크** (S3 미사용)
- 컴퓨트: AWS EC2 기반 컨테이너 배포
- 브라우저 분석: MediaPipe 특징 추출 + 온디바이스 참여도 모델(ONNX), 룰 폴백
- 실시간 전사·팁: SSAFY GMS whisper-1 + LLM
- 사후 멀티모달 분석: SSAFY GMS
- 인증: Google OAuth + JWT(Access 헤더 / Refresh 쿠키)
- 완료 알림: 이메일

서비스 경계는 인증·수업 API, 실시간 미디어, 브라우저 특징 추출·판정, 이벤트 집계·트리거, 실시간 전사·팁, 녹화·병합, 사후 전사·GMS 분석, 타임라인·리포트, 권한·삭제·감사로 나눈다.
